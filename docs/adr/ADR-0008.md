# ADR-0008 — Upload e drag-and-drop sem biblioteca

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

A tela de envio precisa de: seleção múltipla, arrastar e soltar, miniatura por
arquivo e status de envio individual. A demanda pedia ADR para qualquer
biblioteca usada nisso.

O candidato óbvio é `react-dropzone` — é o padrão de fato. Mas vale olhar o que
ele entrega, item a item, contra o que **esta** tela precisa:

| O que react-dropzone dá                       | Precisamos?                                                                |
| --------------------------------------------- | -------------------------------------------------------------------------- |
| Validação de tipo (`accept`) e rejeição       | **Não.** A demanda proíbe: "não implemente validação de tipo de documento" |
| Validação de tamanho (`maxSize`)              | Não pedido                                                                 |
| Estados de arrasto (`isDragActive`)           | Sim — 3 linhas de `useState`                                               |
| `<input multiple>` escondido + click          | Sim — 5 linhas                                                             |
| Normalizar `dataTransfer.files`               | Sim — `Array.from(e.dataTransfer.files)`                                   |
| Suporte a diretórios, paste, `useFsAccessApi` | Não pedido                                                                 |

A restrição que mais pesa é a primeira. A validação de tipo é boa parte do valor
da biblioteca, e é justamente o que o escopo proíbe — a decisão do que é um
documento válido pertence ao modelo de extração, não ao front.

## Decisão

**Nenhuma biblioteca.** `DropZone` usa os eventos nativos `onDragOver`,
`onDragLeave` e `onDrop` mais um `<input type="file" multiple>` escondido.

O componente é o do design system, portado (ADR-0009). O que sobra de código
próprio são ~15 linhas.

Duas escolhas dentro dele:

- **`accept="image/*,application/pdf"` está no input**, mas é _filtro do seletor
  de arquivos_, não validação: um arquivo arrastado de qualquer tipo continua
  passando para `onFiles`. O atributo só evita que o usuário navegue por
  arquivos que obviamente não interessam. Nada é rejeitado pelo front.
- **O input é limpo (`event.target.value = ""`) depois de cada seleção.** Sem
  isso, escolher o mesmo arquivo duas vezes seguidas não dispara `change` na
  segunda vez, e a seleção some sem explicação.

## Um pedido por arquivo

O contrato (ADR-0005) aceita N arquivos num `POST`. A tela mesmo assim envia
**um por requisição**.

Motivo: o requisito é status de envio _por arquivo_. Uma requisição em lote
tem um único desfecho — se ela falha, ou todas as miniaturas mentem dizendo
"falhou", ou todas mentem dizendo "enviado". Com um pedido por arquivo, o
estado de cada miniatura é o desfecho real daquele arquivo, e o reenvio cobre
só o que falhou.

Sequencial, não paralelo, porque é o que a própria copy do design system
promete: "O envio confirma arquivo por arquivo".

## Miniaturas: imagem sim, PDF não

`URL.createObjectURL` dá preview imediato de imagem, sem upload e sem servidor.
Os object URLs são liberados ao remover um item, ao limpar a fila e ao
desmontar a tela — senão uma sessão longa vaza blobs.

**PDF não tem miniatura.** Renderizar a primeira página exige `pdf.js`
(~300 KB) e um worker. Para um ganho estético num escopo que já tem preview de
imagem, não compensa — `FileThumb` cai no glifo de documento, que é o
comportamento que o próprio design system desenhou. Fica registrado como
reversível: se a banca considerar o preview de PDF essencial, é uma dependência
e um ADR.

## Sem barra de progresso real

`FileThumb` mostra a barra indeterminada enquanto envia, não uma porcentagem.

Porcentagem de upload exige `XMLHttpRequest` (o `fetch` não expõe progresso de
envio) ou streams com `ReadableStream`, o que significa abandonar o cliente
tipado de `lib/api/client.ts` só para essa tela. Contra um mock em localhost,
onde o upload é instantâneo, seria complexidade sem sinal.

O requisito é "indicador de status de envio (enviando, enviado, erro)" — os três
estados existem e são visíveis. Porcentagem não foi pedida.

## Alternativas descartadas

- **`react-dropzone`.** Descartada pelo quadro acima: o que ela adiciona além do
  nativo é sobretudo validação, que o escopo proíbe. Vale reabrir se aparecer
  arrastar-pastas ou colar-da-área-de-transferência.
- **`filepond` / `uppy`.** Resolvem o problema inteiro — inclusive progresso,
  retomada e edição de imagem. Descartadas: trazem UI própria, que brigaria com
  o design system, e boa parte do que trazem (crop, rotação, câmera) é
  explicitamente proibida nesta demanda.
- **`XMLHttpRequest` para progresso real.** Ver acima.
- **Enviar tudo num pedido em lote.** Ver "Um pedido por arquivo".

## Custo de reverter

Baixo. `DropZone` tem uma responsabilidade só; trocar o miolo por
`react-dropzone` não mexeria em nenhum outro arquivo, porque a fila
(`features/envio/uploadQueue.ts`) só recebe `File[]` e não sabe de onde vieram.
