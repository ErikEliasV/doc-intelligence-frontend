# ADR-0017 — Campo sem tipo, porque o prompt vai mudar

**Status:** Aceito
**Data:** 2026-09-01

## Contexto

O fato (f) do enunciado é o único que não fala de volume nem de erro: _"o modelo
do fornecedor será trocado de versão em algum momento, e os prompts vão mudar
mais de uma vez ao longo do primeiro ano."_

Ele não pede funcionalidade. Ele diz **qual parte do sistema é instável**, e a
pergunta que faz para a trilha B é: quando o prompt mudar, o front-end precisa
ser reimplantado?

O enunciado dá o exemplo de uma identidade — "nome, filiação, data de
nascimento, número e órgão emissor". É tentador transformar essa lista num tipo:

```ts
interface CamposIdentidade {
  nome: string;
  filiacao: string;
  dataNascimento: string;
  numero: string;
  orgaoEmissor: string;
}
```

Isso dá autocompletar, validação por campo e layout por tipo de documento. E
transforma **cada mudança de prompt numa release coordenada de backend e
front-end** — para a parte do sistema que o enunciado avisou que muda mais de uma
vez por ano.

## Decisão

`ExtractedField` não é tipado por tipo de documento. É uma lista ordenada de
`{ nome, valor, confianca, origem }`, e a interface renderiza o que chegar, na
ordem em que chegar ([`lib/api/types.ts`](../../lib/api/types.ts)).

`CamposExtraidos` faz `campos.map` e nada mais. **Nenhuma tela tem lista de
nomes de campo**, nenhuma tela sabe o que é um RG.

O que isso compra: um prompt novo que passe a extrair "data de expedição" chega
à tela de revisão, editável e com confiança própria, **sem uma linha de
front-end**. O mesmo vale para um campo que deixe de existir, ou para um tipo de
documento que ninguém previu.

`nome` é rótulo humano e vem pronto do backend, em português. É deliberado: quem
muda o prompt muda o rótulo junto, no mesmo lugar, sem passar por um dicionário
de tradução no cliente.

## O que isso custa

Três coisas, e nenhuma delas é hipotética.

**1. Não há validação por campo.** O cliente não sabe que "Data de nascimento"
é uma data, porque não sabe que o campo existe. Toda correção é texto livre. É o
preço principal, e é consciente: validar exige conhecer o campo, e conhecer o
campo é o acoplamento que esta decisão recusa.

**2. Não há layout por tipo.** Um RG e um contrato renderizam com a mesma lista
vertical. Não dá para agrupar "filiação" sob um cabeçalho, nem pôr frente e verso
lado a lado.

**3. `nome` é rótulo e chave ao mesmo tempo.** `PATCH /documents/{id}/campos`
identifica o campo corrigido por `nome`. Se um prompt novo renomear "Número"
para "Número do documento", uma correção em trânsito aponta para um campo que
não existe mais. Hoje isso é 409 ou campo ignorado, dependendo do momento — e
não há teste que o cubra, porque o mock nunca renomeia nada.

## O acoplamento que sobrou

A decisão vale para o contrato. No cliente sobrou uma exceção, e ela é
exatamente do tipo que o fato (f) prevê:

```ts
// features/revisao/CamposExtraidos.tsx
const MONO = new Set(["Data de nascimento", "Número", "Órgão emissor"]);
```

É a regra de conteúdo do design system — número em fonte mono — implementada por
uma lista de nomes fixa no cliente. Se o prompt renomear qualquer um dos três, o
campo **perde a fonte mono em silêncio**.

Falha suave: é tipografia, não dado, e ninguém vê valor errado por causa disso.
Mas é uma lista de nomes de campo dentro de um componente que esta ADR diz não
ter nenhuma, e fingir o contrário seria pior do que registrar.

A correção certa não é uma lista maior. É **metadado no contrato** — um
`formato: "texto" | "numero" | "data"` em `ExtractedField` — que dá mono e
validação sem o cliente aprender nome nenhum. Não entrou agora porque não há
implementação por trás: quem decide o formato de um campo é a extração, e a
extração é dublê. Fica registrado como o caminho, não como dívida de código.

## Alternativas descartadas

- **Schema tipado por tipo de documento.** Dá validação, autocompletar e layout
  por tipo. Descartado pelo custo do fato (f): cada mudança de prompt vira
  release coordenada, e o enunciado diz que serão várias no primeiro ano.
- **Discriminador `tipoDocumento` com registro de tipos conhecidos no cliente,
  caindo para renderização genérica no resto.** Metade do benefício pelo dobro
  do código, e o caminho genérico — o único garantido a rodar quando o modelo
  mudar — seria o menos exercitado dos dois, e o primeiro a apodrecer.
- **Dicionário de rótulos no cliente,** mapeando chave técnica para texto em
  português. Põe o front-end no caminho crítico de toda mudança de prompt para
  ganhar consistência de tradução, que já vem resolvida da origem.

## Custo de reverter

Baixo, e o caminho é aditivo. `formato` entra em `ExtractedField` como opcional:
quem serve, serve; quem não serve, cai no comportamento de hoje. Tipar por
documento depois é mais caro — exige `tipoDocumento` no contrato e um caminho de
renderização por tipo —, mas nada do que existe hoje atrapalha, porque a lista
dinâmica continua sendo o caminho de fallback correto.
