# ADR-0006 — Servir o mock por route handlers do Next.js

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

Não existe API real. O contrato do ADR-0005 precisa de algo por trás dele até
que exista. A demanda pedia para registrar a escolha entre MSW, rotas de API do
Next.js, ou outra abordagem.

Duas restrições moldam a decisão:

1. **ADR-0002.** `features/` importa funções tipadas de `lib/` e nunca sabe se
   por trás há mock ou HTTP. O mock não pode vazar para dentro das telas.
2. **`AGENTS.md`, regra 3.** Nenhuma biblioteca nova sem trade-offs num ADR.

## Decisão

Duas camadas, separadas de propósito:

```
app/api/documents/…        route handlers — adaptador HTTP fino, sem regra
mocks/simulation/engine.ts motor da simulação — toda a lógica, sem HTTP
mocks/store.ts             a instância única que os handlers compartilham
```

O motor não sabe o que é uma requisição. Os handlers não sabem o que é
confiança. Foi isso que permitiu testar a lógica sem subir servidor (25 testes
unitários) e ainda assim ter um HTTP de verdade para o front consumir.

**Zero dependências novas** para servir o mock.

## Por quê route handlers

- **O contrato vira executável.** `curl -F "arquivos=@peticao.pdf"
localhost:3000/api/documents` responde 202. O que o ADR-0005 descreve, este
  servidor faz — verificado ponta a ponta, incluindo 404, 400 e 405.
- **O código do cliente será código de produção.** O front vai fazer `fetch`
  numa URL real. Quando o backend existir, muda a URL base e nada mais. Não há
  caminho de código que só roda com mock.
- **Nenhuma dependência.** Route handlers já vêm no Next.
- **A simulação sobrevive à requisição.** O estado vive num módulo, não numa
  aba do navegador, então dois clientes veem a mesma fila.

## Sem timers: o motor é uma projeção do relógio

A decisão de implementação que mais importa aqui.

O destino de um documento — duração, falhar ou não, confiança dos campos — é
sorteado **uma vez, no upload**. Cada leitura depois disso é uma função pura do
tempo decorrido, sem `setTimeout` em lugar nenhum.

Isso dá três coisas de graça:

- **Teste determinístico.** Um teste injeta um relógio falso e adianta 40
  segundos sem esperar 40 segundos.
- **Leitura idempotente.** Ler duas vezes no mesmo instante devolve o mesmo
  documento. `atualizadoEm` é o instante da transição, não o da leitura.
- **Nada se perde quando a requisição termina.** Um timer pendente morreria com
  o processo que o criou; um prazo guardado não.

## Alternativas descartadas

- **MSW.** É a escolha certa quando se quer interceptar `fetch` sem servidor —
  em testes de componente, ou num front que roda sozinho. Descartada aqui: é
  dependência nova (`AGENTS.md` regra 3) para resolver um problema que o Next já
  resolve, e o service worker adiciona uma camada a mais para depurar. **Vale
  reabrir quando entrarem testes de UI**, onde interceptar `fetch` em jsdom é
  exatamente o caso de uso do MSW — e aí ele conviveria com estes handlers, não
  os substituiria.
- **Só um módulo em memória, sem HTTP.** O mais simples que funcionaria, e
  compatível com o ADR-0002. Descartado porque não exercita o contrato: o
  cliente nunca faria uma requisição, e "a interface consome o contrato" ficaria
  por provar. Erros de serialização e status HTTP só aparecem quando existe HTTP.
- **`json-server` ou similar.** Segundo processo para manter, e não sabe simular
  transição de estado no tempo, que é justamente o ponto.
- **Timers com `setTimeout` no upload.** Foi a primeira forma que considerei.
  Descartada pelos motivos da seção acima — e porque um teste da taxa de erro
  precisaria de 4.000 timers.

## Limitações, declaradas

- **O estado é por processo e some no restart.** Aceitável e esperado num mock.
  Um backend real persiste.
- **`mocks/store.ts` pendura a instância em `globalThis`**, não num `const` de
  módulo, porque o Next reavalia módulos a cada hot reload em desenvolvimento —
  um binding comum esvaziaria a fila a cada edição.

  **Isso tem um custo, observado duas vezes durante o desenvolvimento.** O
  estado sobrevive ao recarregamento, mas as _classes_ que criaram esse estado
  são reavaliadas junto com o módulo. As duas consequências que apareceram:

  1. Depois de acrescentar campos ao registro (`versao`, `presenca`), os
     documentos já guardados continuaram sem eles, e a API respondeu
     `versao: undefined`.
  2. Depois de recarregar `engine.ts`, um `ConflictError` criado pela classe
     antiga deixou de satisfazer `instanceof` contra a classe nova, o handler
     não o capturou, e um conflito que deveria ser **409 virou 500**.

  Nos dois casos o código estava correto e um `next dev` novo resolveu — não é
  bug de produção, onde os módulos são avaliados uma vez. Mas é a armadilha
  desta escolha, e a regra prática é: **mudou a forma do registro ou uma classe
  de erro, reinicie o servidor antes de testar à mão.**

- **Não escala horizontalmente.** Duas instâncias do servidor teriam duas filas.
  Irrelevante em desenvolvimento; seria bloqueante em produção, onde não vai
  rodar.
- **`POST` aceita só `multipart/form-data`.** É o que o navegador manda num
  upload de arquivo. Não há caminho JSON alternativo só para facilitar teste
  manual — seria um segundo caminho de código que o front nunca usaria.

## Custo de reverter

Baixo. O motor não depende de HTTP: trocar o transporte é reescrever
`app/api/documents/`, que é adaptador fino. Os testes continuariam valendo.
