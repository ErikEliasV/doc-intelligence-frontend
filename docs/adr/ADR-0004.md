# ADR-0004 — ESLint + Prettier: divisão de responsabilidade

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

O projeto já vinha com ESLint 9 em flat config, estendendo
`eslint-config-next/core-web-vitals` e `eslint-config-next/typescript`. Não havia
formatador. Sem um, formatação vira ruído de diff e discussão de revisão.

`AGENTS.md` (regra 3) exige ADR antes de qualquer dependência nova. Este ADR
cobre as duas instaladas.

## Decisão

**Uma responsabilidade cada:** Prettier decide forma, ESLint decide correção.
Nenhuma regra de estilo no ESLint.

### Dependências instaladas

| Pacote                            | Por quê                                                                                                                | Custo                                         |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `prettier` (3.9.6)                | Formatador de facto do ecossistema. Remove formatação da revisão de código.                                            | Dev-only. Sem impacto no bundle.              |
| `eslint-config-prettier` (10.1.8) | Desliga as regras do ESLint que conflitam com o Prettier. Sem ele as duas ferramentas brigam em cima do mesmo arquivo. | Dev-only, zero runtime. É config, não plugin. |

Ambas são dev dependencies e não entram no bundle. `eslint-config-prettier` é
carregado **por último** na flat config — a ordem importa, ele precisa vir depois
de tudo que possa ligar regra de estilo.

### Configuração do Prettier

Alinhada ao que já existia no repositório (aspas duplas, ponto e vírgula), para
que a primeira formatação não vire um diff de todo arquivo:
`printWidth: 100`, `trailingComma: "all"`, `endOfLine: "lf"`.

`styles/design-system/` está no `.prettierignore`: o CSS vendorizado precisa
continuar idêntico à origem para poder ser re-sincronizado (ADR-0003).

### Regras adicionadas ao ESLint

Poucas, e cada uma pega uma classe de bug real:

- `@typescript-eslint/no-unused-vars` como **erro**, com escape `^_`. Import
  órfão e variável morta são o resto mais comum de refatoração.
- `no-console` como aviso, permitindo `warn` e `error`. `console.log` esquecido
  em produção.
- `eqeqeq: ["error", "smart"]` — `==` com coerção é fonte de bug silencioso;
  `smart` continua permitindo `== null`.
- `prefer-const`, `no-var`.

Não foram adicionadas regras de ordenação de import: a documentação do Next.js
desaconselha ordenadores automáticos de import, porque a ordem de import
determina a ordem do CSS no bundle
(`01-getting-started/11-css.md`, seção "Recommendations").

### Scripts

```
npm run lint          eslint
npm run lint:fix      eslint --fix
npm run format        prettier --write .
npm run format:check  prettier --check .
npm run typecheck     tsc --noEmit
```

## Alternativas descartadas

- **Biome / oxlint** no lugar dos dois. Mais rápidos, e o design system até
  entrega um `_adherence.oxlintrc.json` pronto para oxlint. Descartado porque
  `eslint-config-next` traz regras específicas do Next (`next/no-img-element`,
  Core Web Vitals) que não têm equivalente, e trocar o linter que já vem
  configurado custaria mais do que portar duas regras de aderência (ADR-0003).
  Vale reavaliar se as regras de aderência crescerem.
- **Prettier rodando como regra do ESLint** (`eslint-plugin-prettier`).
  Descartado: erros de formatação passam a poluir a saída do lint e a execução
  fica visivelmente mais lenta.
- **Nenhum formatador.** Descartado: transfere formatação para a revisão humana.

## Não decidido aqui

Hook de pre-commit (`husky` + `lint-staged`) e CI. Ambos exigem dependência nova
e ganham o seu próprio ADR quando forem pedidos. Até lá a verificação é manual,
pelos scripts acima.

## Custo de reverter

Baixo. Duas dev dependencies, dois arquivos de config, um bloco na flat config.
