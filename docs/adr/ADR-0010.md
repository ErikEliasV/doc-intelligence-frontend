# ADR-0010 — Tailwind em toda a interface, sem estilo inline

**Status:** Aceito
**Data:** 2026-08-31
**Substitui:** a seção 3 do [ADR-0003](ADR-0003.md) (ponte `ds-*`) e o item de
prop surface do [ADR-0009](ADR-0009.md)

## Contexto

O ADR-0003 montou uma ponte do design system para o Tailwind com utilitários
prefixados (`bg-ds-ink-900`). O ADR-0009 portou sete componentes mantendo a
prop surface da origem — inclusive `style?: CSSProperties`, e com todo o visual
escrito como objeto de estilo inline, fiel ao `.jsx`.

O resultado foi incoerente: o projeto declara Tailwind, tem uma ponte construída
para ele, e nenhuma tela usava um utilitário sequer. A ponte existia sem
consumidor.

Duas coisas me levaram ao inline, e as duas tinham solução que eu não tinha
procurado:

1. **Os papéis de tipo do design system são shorthand `font:` composto**
   (`--type-body: var(--weight-regular) var(--size-body)/var(--leading-body) var(--font-ui)`).
   Não existe utilitário Tailwind para a propriedade `font`. Concluí que não
   dava para expressar — e registrei isso no ADR-0003.
2. **Os nomes de token colidem com os namespaces do Tailwind** (`--font-*`,
   `--radius-*`, `--shadow-*`). `@theme inline { --shadow-hard: var(--shadow-hard) }`
   vira auto-referência. Resolvi com o prefixo `ds-`.

O Tailwind v4 resolve as duas com `@utility`, que eu não tinha usado.

## Decisão

Toda a interface em classes Tailwind. Zero `style={{}}`, com uma exceção
declarada abaixo.

Dois mecanismos, para dois problemas:

**`@theme inline` para cores.** Os nomes do design system (`--ink-900`,
`--surface-page`) nunca colidem com o namespace `--color-*` do Tailwind. Logo
**o prefixo `ds-` não era necessário nas cores** — eu havia prefixado demais.
Agora lê natural: `bg-ink-900`, `text-muted`, `border-line-strong`.

**`@utility` para o resto.** Fica fora do namespace de tema, então não há
colisão possível — e resolve o shorthand `font:`:

```css
@utility type-display-2 {
  font: var(--type-display-2);
  letter-spacing: var(--tracking-display);
}
@utility shadow-hard {
  box-shadow: var(--shadow-hard);
}
```

Onde o design system sempre aplica um par junto (fonte + tracking + uppercase
no eyebrow), o utilitário embute o par. Uma classe no call site, não três.

Verificado no CSS emitido: todo utilitário sai como `var(--token)`, nunca
literal. O design system continua fonte única de verdade.

## O press virou `:active`

O `Button` da origem controla o press com `onPointerDown`/`onPointerUp` e
`useState`. Virou a variante `active:` sobre um `@utility pressed`.

Menos código, e mais correto em dois casos que a versão em JS erra: o navegador
não aplica `:active` a botão desabilitado, e o estado não fica preso quando o
ponteiro sai do botão no meio do clique. Como sobrou sem estado, `Button` não
precisa mais de `"use client"`.

Confirmado no build: `.active\:pressed:active{box-shadow:none;transform:translate(var(--press-offset),var(--press-offset))}`.

## `className` no lugar de `style`

Os componentes agora recebem `className`, não `style`. É o desvio de prop
surface que o ADR-0009 dizia não ter — e é obrigatório: manter `style` seria
manter a porta aberta para o inline que esta decisão remove. `className` está na
lista de props que as regras de aderência da origem permitem.

O `Card` perdeu a prop `padding` (que recebia string CSS crua). Padding é classe
do chamador, como qualquer outra decisão de layout.

## A exceção: uma largura inline

`ProgressBar` mantém `style={{ width: "NN%" }}` no modo determinado. É valor
contínuo, não classe — gerar uma classe por porcentagem seria pior. O modo
indeterminado, que é o único usado hoje, é `w-[38%]` e não tem inline nenhum.

## Sem `clsx` + `tailwind-merge`

Um `cn()` de três linhas em `components/cn.ts`, que só filtra e junta.

O par `clsx` + `tailwind-merge` existe para resolver conflito quando a classe do
chamador briga com a do componente (`p-4` contra `p-6`) — e quem decide isso é a
ordem no CSS, não a ordem na string. Em vez de pagar duas dependências,
**os componentes não definem defaults que o chamador precise sobrescrever**:
padding e layout são sempre do chamador. Foi o que fez `ProgressBar` perder a
prop `height`.

Se algum componente precisar de default sobrescrevível, é aí que se reabre
`tailwind-merge` num ADR — não antes.

## Efeito colateral: `app/page.tsx`

A página do `create-next-app` continuava na raiz, com hex cru que a própria
regra de aderência acusava (as duas únicas warnings do lint desde o bootstrap).
Virou `redirect("/envio")`.

Não é tela nova — é o mínimo para a raiz não ser um placeholder num entregável,
e para o lint ficar em zero. Uma home de verdade aparece quando existir o shell
com navegação.

## Alternativas descartadas

- **Manter o prefixo `ds-` em tudo.** O argumento do ADR-0003 (`bg-ds-ink-900`
  denuncia um `bg-zinc-50` perdido) não sobrevive ao custo: prefixo em cada
  classe de cada componente, por um ganho que o lint de aderência já dá.
- **Manter `style` e só converter as telas.** Deixaria os componentes — onde
  está a maior parte do visual — fora da decisão.
- **CSS Modules por componente.** Coerente com o design system ser CSS puro, mas
  o projeto declara Tailwind e o pedido é Tailwind.
- **Redefinir os valores dos tokens dentro de `@theme`,** sem `inline` e sem
  `@utility`. Some a colisão, mas duplica todo valor do design system — duas
  fontes de verdade, que é exatamente o que o ADR-0003 evitou ao vendorizar.

## Custo de reverter

Médio. Voltar ao inline seria reescrever os sete componentes e a tela. Trocar só
o esquema de nomes (reintroduzir `ds-`) é achar-e-substituir mais o bloco
`@theme`.
