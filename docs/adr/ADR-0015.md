# ADR-0015 — `Button` ganha `href`, cobrando a previsão do ADR-0009

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

O design system põe ações no header de cada tela. No `index.html` do kit da
origem elas são exatamente:

```jsx
// envio
<Button variant="inverse" size="sm" iconRight={<Icon name="arrow-right" size={13} />}>Ir ao painel</Button>

// painel
<><Badge tone="neutral">812 hoje</Badge>
  <Button variant="outline" size="sm" iconLeft={<Icon name="upload" size={13} />}>Enviar mais</Button></>
```

As duas são navegação entre rotas. No protótipo da origem elas chamam
`setView(...)` num `<button>`; aqui precisam levar a `/acompanhamento` e
`/envio`.

O [ADR-0009](ADR-0009.md) registrou o desvio nº 3 nestes termos:

> **`Button` não tem a prop `as`.** A origem permite `as="a"` para renderizar
> link. Nenhuma tela desta entrega precisa, e um componente polimórfico correto
> em TypeScript custa bem mais do que aparenta. **Entra quando houver
> botão-link.**

Chegou o botão-link.

## Decisão

`Button` aceita `href`. Com ele renderiza `next/link`; sem ele segue `<button>`.

O tipo é uma **união discriminada em `href`**, não um `as` polimórfico:

```ts
type ButtonComoBotao = ButtonComum & ButtonHTMLAttributes<HTMLButtonElement> & { href?: never };
type ButtonComoLink = ButtonComum &
  Omit<AnchorHTMLAttributes<HTMLAnchorElement>, "href"> & { href: string };
export type ButtonProps = ButtonComoBotao | ButtonComoLink;
```

## Por quê assim

- **`href?: never` no lado botão é o que faz o estreitamento funcionar** em
  tempo de execução (`rest.href !== undefined`) e em tempo de compilação.
- **Impede combinações sem sentido.** `disabled` não é oferecido num link;
  `type="button"` não vai parar num `<a>`. Um `as` genérico permitiria as duas.
- **Custa uma união de dois membros, não polimorfismo de verdade.** A ressalva do
  ADR-0009 — "custa bem mais do que aparenta" — vale para `as` aceitando qualquer
  elemento. A necessidade real é um tipo a mais.
- **Os dois ramos são exercitados.** É a diferença entre isto e o superset que
  recusei para o `SidebarNav` no [ADR-0013](ADR-0013.md): lá o ramo `<button>`
  nasceria sem nenhuma tela que o usasse.

Pelo mesmo motivo do ADR-0013: um `<button>` com `router.push` não abre em nova
aba, não tem link para copiar e não recebe prefetch.

## Um desvio de ícone

A origem pede `<Icon name="upload" />`. O `Icon` portado não tem esse glifo — tem
`upload-cloud`, que é o que o `DropZone` já usa para o mesmo conceito nesta
aplicação. Usei `upload-cloud`. Acrescentar o `upload` seria copiar os paths do
`lucide-static` na versão fixada (o ADR-0009 proíbe desenhar à mão), e um segundo
glifo para a mesma ideia dentro do mesmo produto não se paga.

## A cópia é a da origem

**"Ir ao painel"**, não "ir para painel". **"Enviar mais"**. Ambas verbos, como a
regra de conteúdo do design system manda.

## Alternativas descartadas

- **`<Link>` embrulhando `<Button>`.** `<a><button></button></a>` é HTML
  inválido e o comportamento de clique fica indefinido entre navegadores.
- **Exportar a receita de classes e usar `<Link className={...}>` nas telas.**
  Não mudaria a prop surface do `Button` — atraente. Descartado porque a
  montagem dos ícones à esquerda e à direita passaria a ser copiada em cada
  chamada, que é exatamente o que o componente existe para não fazer.
- **`router.push` num `<button>`.** Mais barato de todos, e perde as três
  affordâncias de link pelas quais o ADR-0013 já tinha pago.

## Custo de reverter

Baixo. Tirar `href` volta o tipo a uma interface só; as duas chamadas que o usam
viram `<Link>` com classes copiadas. Nada do que já existia mudou: toda chamada
sem `href` renderiza o mesmo `<button>` de antes, o que os testes fixam.
