# ADR-0007 — Vitest como runner de testes

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

A demanda pediu testes unitários da lógica do mock. Não havia runner no projeto.
`AGENTS.md`, regra 3: nenhuma biblioteca nova sem trade-offs num ADR.

O que precisa ser testado hoje é TypeScript puro em ambiente Node — o motor da
simulação, sem DOM e sem React. Mas o projeto é front-end, e testes de
componente vêm depois; escolher agora um runner que não sirva para React seria
escolher duas vezes.

## Decisão

`vitest` (4.1.11), uma dependência de desenvolvimento. Config em
`vitest.config.mts`.

```
npm test         vitest run
npm run test:watch
```

## Por quê

- **Lê TypeScript sem configuração.** Nem `ts-jest`, nem Babel, nem passo de
  build antes do teste.
- **Serve o próximo passo.** Quando entrarem testes de componente, o mesmo
  runner cobre com `environment: "jsdom"` e Testing Library. Não vai haver uma
  segunda decisão de runner.
- **API compatível com Jest** (`describe`/`it`/`expect`), então o conhecimento
  do time transfere.
- **Dev-only.** Não entra no bundle.

### Detalhes que custaram tempo e ficam registrados

- **O arquivo de config precisa ser `.mts`.** Como `.ts`, o Vite carrega como
  CommonJS e avisa que sintaxe ESM não é suportada pelo loader nativo. Renomear
  resolve.
- **O alias `@/*` é declarado à mão** em `resolve.alias`, espelhando o
  `tsconfig.json`, em vez de instalar `vite-tsconfig-paths`. Uma dependência a
  menos para duplicar uma linha.
- **`npm run typecheck` virou `next typegen && tsc --noEmit`.** Não é sobre
  testes, mas foi descoberto aqui: `RouteContext<'/api/documents/[id]'>` é um
  tipo **gerado** pelo Next, então `tsc` sozinho falha num checkout limpo. Sem
  o `typegen` antes, o typecheck quebra em CI e passa na máquina de quem acabou
  de rodar `next build`.

## O que os testes cobrem

25 testes em `mocks/simulation/engine.test.ts`, todos no motor — nenhum em UI,
como pedido.

Duas técnicas, por razões diferentes:

- **RNG constante** para os casos determinísticos: `0.0` sempre falha, `0.2`
  sempre cai em confiança baixa, `0.99` sempre sai `pronto`. Cada caminho fica
  fixado sem depender de sorte.
- **PRNG semeado (mulberry32)** para as taxas, com 4.000 documentos e tolerância
  de ±3 pontos. Semeado para que uma falha seja reproduzível; com tolerância
  para não quebrar se a ordem dos sorteios mudar num refactor.

As asserções de taxa foram verificadas por mutação, não só executadas: subir
`errorRate` de 0.15 para 0.40 quebra o teste de falha; subir `lowConfidenceRate`
de 0.30 para 0.60 quebra o de conferência. Um teste de taxa que passa com o
valor errado não testa nada.

## Alternativas descartadas

- **Jest.** Padrão da indústria e o time provavelmente já conhece. Descartado:
  com TypeScript e ESM exige `ts-jest` ou Babel mais configuração, e é
  visivelmente mais lento. Não traz nada que compense.
- **`node:test`, do runtime.** Zero dependências, o que é atraente sob a regra 3. Descartado: rodar TypeScript ainda depende de type stripping experimental,
  e não cobre teste de componente — a segunda decisão de runner viria em poucas
  semanas.
- **Nenhum teste, só verificação manual por `curl`.** Fiz a verificação por
  `curl` de qualquer forma (ADR-0006), mas ela não pega taxa estatística: 15% de
  erro não se observa em três requisições.

## Custo de reverter

Baixo. Uma dependência, um arquivo de config, dois scripts. A sintaxe dos testes
é quase idêntica à do Jest, então migrar seria mecânico.
