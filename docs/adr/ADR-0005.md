# ADR-0005 — Contrato em OpenAPI, não em markdown

**Status:** Aceito — regra de status emendada pelo [ADR-0012](ADR-0012.md)
**Data:** 2026-08-31

## Contexto

A demanda pedia para documentar o contrato "como se fosse a especificação para o
backend seguir", e deixou a escolha entre `openapi.yaml` e um markdown em
`docs/api-contract.md`.

A diferença entre as duas opções não é de formato, é de audiência. Um markdown é
escrito para uma pessoa ler uma vez. Uma especificação OpenAPI é escrita para
uma pessoa ler **e** para uma máquina consumir — e o pedido diz explicitamente
que alguém vai implementar isto depois.

## Decisão

`docs/api/openapi.yaml`, OpenAPI 3.1. Sem markdown paralelo.

A prosa que um markdown teria não foi descartada: ela vive nos campos
`description` do próprio spec, que aceitam markdown. O diagrama do ciclo de vida
e a regra do limiar de confiança estão lá, no `info.description`.

## Por quê

- **Um backend consegue partir dela.** OpenAPI gera stubs de servidor,
  clientes tipados e coleções de teste. Um markdown gera uma leitura.
- **É verificável.** O spec é parseável, então erro de referência e enum
  divergente aparecem numa checagem automática — coisa que prosa não permite.
  Rodei essa checagem: 9 `$ref`, nenhum quebrado.
- **Não há dois lugares dizendo a mesma coisa.** Um markdown ao lado do spec
  viraria a segunda fonte de verdade, e a que ninguém atualiza.

## O acoplamento que isto cria

`docs/api/openapi.yaml` e `lib/api/types.ts` descrevem o mesmo contrato e
**precisam mudar juntos**. Os dois arquivos dizem isso no topo.

Hoje nada automatiza essa sincronia. Considerei um teste que lê o YAML e compara
enum e propriedades obrigatórias com os tipos, mas isso exige um parser de YAML
em JavaScript — dependência nova, ADR novo, para um risco que hoje é de dois
arquivos. Fica registrado como pendência: se o contrato crescer, o teste de
sincronia passa a valer mais que a dependência.

## Alternativas descartadas

- **`docs/api-contract.md`** (o caminho sugerido). Mais rápido de escrever, mais
  agradável de ler em diff. Descartado porque não é consumível por ferramenta, e
  o destinatário declarado do documento é quem vai implementar o backend.
- **Os dois.** Duas fontes de verdade sobre o mesmo contrato. É o pior dos
  mundos: divergem em silêncio.
- **Gerar o OpenAPI a partir de schemas Zod.** Tira a duplicação de vez, e é o
  que eu faria num projeto com validação em runtime. Descartado agora: exige
  `zod` + `zod-to-openapi`, duas dependências, para um contrato de 3 endpoints
  que ainda não valida nada em runtime. Vale reabrir quando entrar validação de
  entrada de verdade.

## Custo de reverter

Baixo. Converter o spec em markdown é mecânico; o conteúdo já está escrito.
