# ADR-0012 — Correção e confirmação separadas, com lock otimista

**Status:** Aceito
**Data:** 2026-08-31
**Emenda:** a regra de status do [ADR-0005](ADR-0005.md)

## Contexto

Duas pessoas do atendimento podem abrir o mesmo item de conferência ao mesmo
tempo. O que não pode acontecer: a correção de uma sumir sem ninguém perceber.

E uma decisão de produto tomada junto: **salvar não conclui**. `PATCH` grava a
correção, `POST /confirmar` fecha o documento. Isso permite alguém corrigir
metade dos campos, sair, e outra pessoa terminar — que é como um escritório
funciona quando quem digita não é quem responde pelo documento.

## Decisão

### 1. O status deixa de ser derivado

O ADR-0005 dizia que um documento está em `em_conferencia` **se e somente se**
algum campo tem confiança abaixo de 0.75, e o motor re-derivava isso a cada
leitura.

Isso é incompatível com a decisão acima: um `PATCH` que corrige o campo ruim
faria o documento se fechar sozinho na leitura seguinte.

A regra do limiar passa a valer **só na extração** — ela decide o status
inicial. Depois disso o status é guardado, e só `confirmar` o move.

```
extração  ──0.75──▶  em_conferencia ──PATCH──▶ em_conferencia ──confirmar──▶ pronto
                            │                        ▲
                            └────────────────────────┘
                               (quantas vezes quiser)
```

### 2. O campo corrigido guarda a confiança do modelo

`ExtractedField` ganha `origem: "modelo" | "humano"`. A `confianca` **nunca** é
sobrescrita.

A alternativa óbvia — e o que o kit do design system faz — é subir o campo
corrigido para 100%. Foi descartado: um valor que uma pessoa digitou não ficou
mais confiante, ficou autoritativo. Guardar o 38% original é o registro de onde
o modelo falhou, que é exatamente o dado que serviria para avaliá-lo depois.

Consequência boa e não planejada: o painel de acompanhamento continua honesto.
Um documento corrigido mas não confirmado segue exibindo a confiança baixa —
porque ele _ainda_ depende de alguém assinar embaixo.

A interface resolve mostrando um selo "Corrigido" no lugar do medidor: o 38% é
verdade sobre o modelo, e não diz nada sobre o valor que está ali agora.

### 3. Duas defesas contra concorrência, com papéis diferentes

**`versao` — a correção.** Todo `PATCH` e `POST /confirmar` manda a versão que
leu. Divergência é **409**, nunca sobrescrita. O 409 vem **com o documento
atual** no corpo: a interface precisa mostrar o que a outra pessoa mudou, e
obrigar um segundo `GET` seria pedir de novo o que já temos.

**`revisaoEmAndamento` — o aviso.** `POST /documents/{id}/revisao` registra que
alguém abriu o documento, e a segunda pessoa vê "também está nesta tela" antes
de gastar cinco minutos digitando.

As duas existem porque resolvem problemas diferentes: a versão evita perder
trabalho, a presença evita _fazer_ trabalho perdido.

**O aviso não bloqueia.** Um lock rígido num sistema sem autenticação e sem
encerramento confiável de sessão prende documentos atrás de quem fechou o
notebook. A presença expira em 60s justamente para não virar isso.

### 4. Como a tela absorve um conflito

Ao receber 409, a tela **não recarrega**. Ela adota o documento que veio no
corpo e mantém o rascunho não salvo por cima: os campos que a pessoa estava
editando continuam como ela deixou, os que ela não tocou passam a mostrar os
valores da outra pessoa. Recarregar jogaria fora o trabalho em andamento — que
é o mesmo problema que o lock existe para evitar.

## O que seria feito em produção real

O desenho acima **é** o desenho de produção; o que muda é onde cada peça mora.

| Aqui                                         | Em produção                                                                                                                                          |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `versao` como inteiro no registro em memória | O mesmo, como coluna com constraint — ou `ETag` + `If-Match`, que é a forma HTTP padrão do mesmo mecanismo                                           |
| Comparação de versão dentro do processo      | `UPDATE ... WHERE id = ? AND versao = ?` e checar as linhas afetadas: a atomicidade fica no banco, não na aplicação                                  |
| `x-revisor-id` gerado pelo cliente           | **Ignorado.** O usuário vem do token autenticado. Confiar num cabeçalho permitiria se passar por outra pessoa                                        |
| Presença num `Map` do processo               | Chave em Redis com TTL, ou uma tabela `revisoes_ativas` varrida por job. O TTL continua obrigatório                                                  |
| Segunda pessoa descobre o conflito ao salvar | O mesmo, mais um canal de presença ao vivo se o volume justificar (não justifica — ver ADR-0011)                                                     |
| Bytes do documento no processo               | Object storage com URL assinada de curta duração                                                                                                     |
| Sem trilha de auditoria                      | Tabela de eventos: quem corrigiu qual campo, quando, de qual valor para qual. `origem` é o começo disso, mas não guarda o valor anterior nem o autor |

O 409 permaneceria idêntico do ponto de vista do cliente, que é o que importa:
o contrato já descreve o comportamento certo, e trocar a implementação não muda
uma linha da tela.

## Limitações conhecidas

1. **A presença some no restart** e é por processo — herdado do ADR-0006.
2. **Não há trilha de quem corrigiu.** `origem` diz que foi um humano, não qual
   humano nem qual era o valor antes. Num escritório de advocacia isso
   provavelmente é requisito, e é mudança de contrato.
3. **`revisaoEmAndamento` só mostra uma pessoa.** Com três abertas, a terceira
   vê apenas a primeira. Bastaria uma lista; não vale a complexidade agora.
4. **A tela não avisa em tempo real** que a outra pessoa salvou — só ao tentar
   salvar. Um poll na revisão resolveria, ao custo que o ADR-0011 já discute.
5. **Confirmar não exige ter revisado nada.** É deliberado: quem revisa decide.
   Um fluxo mais rígido exigiria marcar campo a campo como conferido.

## Alternativas descartadas

- **`PATCH` que fecha o documento sozinho quando todos os campos ficam acima do
  limiar.** Era o comportamento que o ADR-0005 já tinha implementado, antes de
  esta decisão existir: `deriveStatus` rodava a cada leitura. Mais simples, e
  errado assim que existe correção humana — ninguém assina embaixo.
- **Lock pessimista** (o segundo a chegar não edita). Descartado: sem
  autenticação nem encerramento de sessão, documentos ficam presos. E o volume
  não justifica — a colisão é rara.
- **Last-write-wins.** É o comportamento que o requisito proíbe.
- **Merge automático campo a campo** (aceitar as duas correções se forem em
  campos diferentes). Tentador e implementável, mas resolve o caso fácil e
  esconde o difícil: em campos iguais alguém ainda precisa decidir, e aí a
  interface teria dois caminhos em vez de um.

## Custo de reverter

Baixo para a interface. Médio para o contrato: `origem` e `versao` são campos
obrigatórios do `Document`, e removê-los quebraria os três consumidores.
