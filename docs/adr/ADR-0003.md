# ADR-0003 — Design system vendorizado + ponte para Tailwind v4

**Status:** Aceito
**Data:** 2026-08-31

## Contexto

O design system do DOC Intelligence vive num projeto do `claude.ai/design`
(`8541ef4f-9db6-43f0-a4bc-b87fa37ac7a9`), lido pelo MCP `DesignSync`. Ele
contém: 7 arquivos de token CSS, 24 componentes React (`.jsx` + `.d.ts` +
`.prompt.md`), 17 cards de guideline, um kit de 5 telas, e um
`_adherence.oxlintrc.json` com as regras que policiam o uso.

Não é um pacote npm. Não há versão publicada, nem `package.json`, nem
changelog. É uma pasta de arquivos que evolui na origem.

O projeto local usa **Tailwind v4**, que não tem `tailwind.config.js` — o tema
é declarado em CSS via `@theme` (ver ADR-0001).

## Decisão

### 1. Vendorizar os tokens, byte a byte

Os arquivos de `tokens/` foram copiados literalmente para
`styles/design-system/tokens/`. Não são editados à mão. Overrides locais moram
fora de `tokens/`, para que uma re-sincronização seja uma substituição de
arquivos e não um merge.

`styles/design-system/index.css` reproduz o `styles.css` da origem com duas
mudanças declaradas:

- `@import "./x.css"` em vez de `@import url("./x.css")`. O bundler do Tailwind
  só faz inline da primeira forma; um `@import` deixado no lugar cai depois das
  regras do Tailwind e vira CSS inválido (o build acusa
  _"@import rules must precede all rules"_).
- `tokens/fonts.css` foi substituído — ver item 2.

### 2. Fontes por `next/font/google`, não pelo CDN

A origem carrega Playfair Display, Archivo e IBM Plex Mono com um `@import` para
`fonts.googleapis.com`. Aqui elas são declaradas em `app/layout.tsx` via
`next/font/google`, e `styles/design-system/next-font.css` reaponta os três
tokens de família para as variáveis geradas, mantendo as pilhas de fallback
originais.

Motivo: `next/font` auto-hospeda os arquivos (verificado: 29 `.woff2` no build),
elimina a requisição a um terceiro, e gera métricas de fallback que removem
layout shift. O próprio README da origem prevê a troca — ele diz para substituir
o `@import` por fontes locais quando os arquivos reais chegarem.

**Pendência herdada:** as três famílias são substitutas do Google Fonts, não as
fontes reais da marca. A origem pede confirmação. Quando os arquivos reais
chegarem, muda só `app/layout.tsx`.

### 3. Ponte para Tailwind com prefixo `ds-`

`app/globals.css` mapeia os tokens em `@theme inline`, com **todas as chaves
prefixadas com `ds-`**: `bg-ds-ink-900`, `font-ds-display`, `shadow-ds-hard`,
`rounded-ds-pill`.

O prefixo não é cosmético. Os nomes de token do design system caem em
namespaces que o Tailwind também usa (`--font-*`, `--radius-*`, `--shadow-*`,
`--space-*`, `--leading-*`, `--tracking-*`, `--ease-*`). Sem prefixo, a chave
`--shadow-hard` expande para `--shadow-hard: var(--shadow-hard)` — uma
auto-referência que só resolve porque o CSS vendorizado é emitido _depois_ do
bloco de tema. Isso funcionava, mas dependia da ordem de emissão do Tailwind,
que é detalhe de implementação: uma inversão futura apagaria fontes, sombras e
raios silenciosamente. O prefixo remove a dependência, e o build passou a ser
verificável (`grep` por auto-referências no CSS emitido não retorna nada).

Efeito colateral desejado: `bg-ds-ink-900` ao lado de um `bg-zinc-50` perdido
mostra na hora qual dos dois é escolha do design system.

Nem tudo virou utilitário. Ficaram de fora, para uso como `var(--token)`:

- **papéis de tipo** (`--type-body`, `--type-masthead`): são shorthand `font:`
  composto, não existe utilitário equivalente;
- **cores de status e confiança**: consumidas dentro de componentes;
- **movimento**: `--duration-*`, `--ease-*`, `--transition-control`;
- **espaçamento**: a escala base de 4px do design system já coincide com a do
  Tailwind, remapear seria ruído.

### 4. Aderência: subconjunto das regras, no ESLint

`_adherence.oxlintrc.json` é config de **oxlint**, que não está no projeto.
Duas regras foram portadas para o ESLint (`no-restricted-syntax` aceita os
mesmos seletores esquery), limitadas a `app/`, `components/` e `features/`:

- hex cru → use token de cor;
- `font-family` fora das três famílias do design system.

Ficaram de fora, deliberadamente:

- **A regra de `px` cru.** Dispararia em valores arbitrários do Tailwind e em
  qualquer `style` inline legítimo. Ruído alto, sinal baixo.
- **As ~30 regras de props de componente** (`<Button variant>` só aceita
  `primary|inverse|...`). Elas só fazem sentido quando os componentes existirem
  no projeto — e aí os `.d.ts` do design system dão a mesma garantia em tempo de
  compilação, melhor. Serão reavaliadas quando os componentes forem portados.

Verificado: a regra de hex já pegou dois valores em `app/page.tsx` (o resto da
página padrão do `create-next-app`).

## Alternativas descartadas

- **Traduzir os tokens para `@theme` do Tailwind, sem CSS vendorizado.**
  Perderia a rastreabilidade com a origem: cada re-sincronização viraria uma
  tradução manual, com risco de divergência silenciosa.
- **Consumir o design system só por `var(--token)`, sem ponte Tailwind.**
  Funciona, mas num projeto com Tailwind obrigaria `style={{}}` inline em todo
  componente. A ponte é a integração.
- **Copiar o `_ds_bundle.js` e usar os componentes direto.** São `.jsx` sem
  tipos no runtime e presumem um ambiente que não é o do App Router. Ver
  "Fora de escopo".
- **Git submodule / subtree apontando para a origem.** A origem não é um
  repositório git.

## Fora de escopo nesta decisão

Os 24 componentes React, o kit de 5 telas (`ui_kits/`) e os previews HTML
(`DOC Intelligence App (offline).html`, `thumbnail.html`) **não** foram
importados. Dois motivos: a instrução desta etapa era não criar nenhuma tela, e
o kit cobre 5 telas enquanto o escopo da entrega são 3 (`AGENTS.md`, regra 1).
Portar os componentes é uma decisão própria e ganha o seu próprio ADR.

## Custo de reverter

Baixo para a ponte Tailwind (um bloco `@theme` em um arquivo). Baixo para as
fontes (um arquivo). Alto só se os componentes forem portados e passarem a
depender da forma dos tokens — o que ainda não aconteceu.
